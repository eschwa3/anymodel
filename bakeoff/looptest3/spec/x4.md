## X4 Billing: late fees, statement export, credit notes

Each `### X4.K` sub-section below is a self-contained contract for one
billing feature. Implement exactly the named public API in the named NEW
module; do not modify any existing jobsched file. New modules may import
and call existing code (`jobsched.billing`, `jobsched.utils.money`,
`jobsched.repository`, `jobsched.errors`, ...). Money is integer cents
everywhere; the rounding rule is **half-up**, applied once at finalization,
via `jobsched.utils.money.round_half_up` (the same helper
`jobsched.billing.compute_tax` already uses). Follow the repo conventions
in AGENTS.md: stdlib only, `from __future__ import annotations`, absolute
imports, raise `jobsched.errors` exceptions for anything a caller catches.

### X4.1 Late-fee computation from days overdue

Purpose: compute the late fee owed on a paid-late invoice total from the
number of days it is overdue, with a grace period, a daily rate, and a cap.

New module: `jobsched/billing_latefees.py` (new file; existing files untouched).

Public contract (exact signature):

```python
def late_fee_cents(
    invoice_total_cents: int,
    days_overdue: int,
    grace_days: int = 5,
    daily_rate_bp: int = 50,
) -> int
```

- `daily_rate_bp` is the daily fee rate in basis points of
  `invoice_total_cents` (50 bp = 0.5% of the total per chargeable day).
- `grace_days` is the number of overdue days that accrue nothing.
- Returns the late fee in integer cents; 0 means no fee.

Behaviour rules:
1. Only days beyond the grace period accrue: `chargeable_days =
   max(0, days_overdue - grace_days)`; `days_overdue <= grace_days` → fee 0.
2. The exact fee is `invoice_total_cents * daily_rate_bp * chargeable_days / 10000`,
   rounded **half-up once** via `jobsched.utils.money.round_half_up`
   (do not round per-day).
3. Cap: the fee never exceeds `invoice_total_cents`, however many days or
   how high the rate.
4. Validation — raise `jobsched.errors.ValidationError` when any of:
   `invoice_total_cents < 0`; `days_overdue < 0`; `grace_days < 0`;
   `daily_rate_bp < 0`.
5. Edge cases: `invoice_total_cents = 0` → fee 0 for any `days_overdue`;
   boundary `days_overdue == grace_days` → 0 and `days_overdue == grace_days + 1`
   → the fee for exactly one chargeable day; rounding example — total 333,
   default rate, one chargeable day: 333 * 50 / 10000 = 1.665 → fee 2 cents.

Existing behaviour and existing tests must keep passing; this feature only
adds a new module and changes nothing else.

### X4.2 Plain-CSV invoice statement export

Purpose: produce a single invoice as a CSV statement string that a
downstream consumer can parse, mirroring the style of
`jobsched/reports/legacy_export.py` (csv module + StringIO, no files).

New module: `jobsched/reports/invoice_export.py`
(new file; existing files untouched; `jobsched/reports/` is a package).

Public contract (exact signature):

```python
def export_invoice_csv(conn: sqlite3.Connection, invoice_id: int) -> str
```

- Returns the CSV text for invoice `invoice_id`, read through
  `jobsched.repository.InvoiceRepository(conn).get(invoice_id)`.
- A missing invoice raises `jobsched.errors.NotFoundError` (propagated from
  `InvoiceRepository.get`; do not catch and re-wrap it).

Output format — built with `csv.writer` into a `StringIO` using the default
dialect (so rows are CRLF-terminated and fields containing commas/quotes are
standard-quoted), containing exactly:
1. Header row: `invoice_id,customer_id,period_start,period_end,currency,description,quantity,amount_cents`
2. One row per stored line item, in stored order (the order
   `InvoiceRepository.get` returns them): the five invoice fields
   (`invoice.id`, `invoice.customer_id`, `invoice.period_start`,
   `invoice.period_end`, `invoice.currency`), then the item's
   `description`, `quantity`, `amount_cents`.
3. A final row: the same five invoice fields, then the literal description
   `TOTAL`, an empty `quantity` (empty string), and `invoice.total_cents`.

Behaviour rules:
1. Amounts are raw integer cents (e.g. `2000`), never formatted strings
   like `20.00 USD`; `total_cents` on the TOTAL row is the stored
   `invoice.total_cents`, not recomputed from the line items.
2. The TOTAL row is always present, even for an invoice with zero line
   items (then the output is exactly header + TOTAL row).
3. Every row has exactly the 8 header columns.

Existing behaviour and existing tests must keep passing; this feature only
adds a new module and changes nothing else.

### X4.3 Credit notes against an invoice

Purpose: let a caller record partial or full credits against a stored
invoice and read back the remaining outstanding balance.

New module: `jobsched/billing_credits.py` (new file; existing files untouched).
No migration file: the module owns its `credit_notes` table, created lazily
with `CREATE TABLE IF NOT EXISTS` executed on the connection the caller
passes (columns exactly: `id INTEGER PRIMARY KEY AUTOINCREMENT`,
`invoice_id INTEGER NOT NULL REFERENCES invoices(id)`,
`amount_cents INTEGER NOT NULL`, `reason TEXT NOT NULL DEFAULT ''`,
`created_at TEXT NOT NULL`). All queries parameterized; commit after insert.

Public contract (exact signatures):

```python
@dataclass
class CreditNote:
    id: int
    invoice_id: int
    amount_cents: int
    reason: str
    created_at: str

def add_credit_note(conn: sqlite3.Connection, invoice_id: int, amount_cents: int, reason: str = "") -> CreditNote
def list_credit_notes(conn: sqlite3.Connection, invoice_id: int) -> list[CreditNote]
def outstanding_balance(conn: sqlite3.Connection, invoice_id: int) -> int
```

Behaviour rules:
1. Each function first ensures the `credit_notes` table exists (lazy
   `CREATE TABLE IF NOT EXISTS` on the passed connection), then resolves the
   invoice via `jobsched.repository.InvoiceRepository(conn).get`, so a
   missing invoice raises `jobsched.errors.NotFoundError` from all three.
2. `add_credit_note` raises `jobsched.errors.ValidationError` when
   `amount_cents <= 0` (checked before the invoice lookup, so an invalid
   amount raises ValidationError even for a missing invoice). It returns the
   stored `CreditNote` with its new id and `created_at` set to
   `jobsched.utils.time.utcnow().isoformat()` (timezone-aware).
3. `add_credit_note` raises `jobsched.errors.ConflictError` — inserting
   nothing — when the sum of the invoice's existing credit amounts plus
   `amount_cents` would exceed `invoice.total_cents`; crediting exactly the
   invoice total is allowed.
4. `list_credit_notes` returns the invoice's notes ordered by id (insertion
   order); an invoice with no notes yields `[]`.
5. `outstanding_balance` returns `max(0, invoice.total_cents - sum of the
   invoice's credit amounts)`.
6. Edge cases: a fresh database (table absent) works on the first call via
   the lazy create; `reason` defaults to `""`; amounts are integer cents.

Existing behaviour and existing tests must keep passing; this feature only
adds a new module and changes nothing else.
